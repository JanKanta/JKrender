1 How JKrender works

A normal Nuke render runs in one process that computes the whole script frame by frame. One Nuke rarely uses all 32 threads of the CPU, though. So JKrender starts several Nuke processes side by side. Each opens the script only once and then gets pieces of work, called chunks: for example 10 frames in a row.

Three numbers that decide the speed

Processes

How many Nuke processes run at once (for all renders together). More processes do more work at once, but also take more RAM and VRAM.

Threads

How many CPU threads each process gets (Nuke -m). Processes × Threads should come to about the thread count of the PC (32 here).

Cache

The cache limit of one process in GB (Nuke -c). A process really takes more. How much, System › RAM shows.
The default is 8 processes × 4 threads. Heavy comp scripts that one Nuke already fills (Defocus, Denoise) are often faster on 4 × 8 and take half the RAM. Scripts whose VRAM grows want fewer processes. What is best for your script, Test this script measures (chapter 12).

Where things are kept

WhatWhere
Settings~/.nuke/JKrender/settings/settings.json (every user has their own). Older versions kept them in ~/.jkrender; JKrender moves them on its first start.
Render logs~/.nuke/JKrender/log/: one folder per render (script snapshot, job, the log of every Nuke process and report.json). Older than 15 days are deleted.
Test results~/.nuke/JKrender/settings/test_results

2 Installing and starting from Nuke

Install (once)

1Copy the whole JKrender folder into %USERPROFILE%\.nuke\. Downloaded from GitHub as a zip, it is called JKrender-main: rename it to JKrender.

2Add this line to ~/.nuke/init.py (create the file if it is not there):

nuke.pluginAddPath("./JKrender")

3Restart Nuke. On the first start, JKrender asks to download numpy and OpenEXR for the EXR preview (about 15 MB). If you say no, rendering still works, only without the EXR preview. To be asked again, delete the file lib/DECLINED.

Optional: for details and the player of MOV/MP4, put ffprobe/ffmpeg on PATH (winget install ffmpeg). Nuke 16 is needed (PySide6).

A new version: copy the new files over the old ones. The lib, log and settings folders stay.

What happens when you send it

Snapshot: the script is rendered as it was when you sent it. You can keep working and saving in Nuke straight away; the running render is not affected. To render a changed script, send it from Nuke again: the newer send replaces the old card.
Cache question: when a Nuke is open, Render asks whether to clear its buffers, playback cache and Blink cache, so the render has more memory. The default answer is No, and the render starts either way. The disk cache is not touched. After updating JKrender, restart Nuke once for this to work.

4 Render cards and the control row

A render card

Every Write sent is one card: number, script name, Write name, a progress bar and the state (Ready, Waiting, Rendering, Paused, Checking output, Done, Failed, Stopped). A click picks the card and the whole window then shows that render. Shift+click picks several cards; Render, Pause and Stop then act on all of them, and Render again on finished ones too (it asks once for all). The × closes the render; the frames on disk stay. A red card: the render has an error (it failed, Nuke did not render a frame, broken frames, a Nuke error, a process crashed), also while it renders; the card's tooltip says which. A process closed for RAM or VRAM is not an error.

Renders share one budget of processes. At most as many run side by side as Settings Max renders at once says (default 3); the processes are shared between them (8 → 4 + 4 → 3 + 3 + 2).

The card on the right: ALL RENDERS DONE IN

When all renders that run or wait should be done, at the speed the PC renders now. Under it: when they end, how long they have run and how many frames are left. When all are through, the card shows ALL RENDERS TOOK: how long it all took.

Each little box is one frame, grouped by chunks (C01, C02…). A click on a frame opens it in the preview. Colours:

Render again: everything, or only what is missing

When the render has frames on disk and you click Render again, it asks: Only missing (the default) renders only the frames missing or broken; the others are skipped and dark green in the map. All frames again renders everything again, Cancel nothing. A movie (MOV, MP4) does not ask: a movie is one file and is rendered whole.

With several cards picked with Shift it asks once for all (e.g. 27 of 27 frames of 3 renders…). Frames that were on disk when the render opened, or from the run before Stop, are dark green. In Output the filter Rendered then shows only the frames of this run, All all of them.

6 The Output panel: preview and frames

Preview

  • Mouse wheel: zoom, dragging moves the image.
  • Double click: back to the whole frame. When it already is, the preview grows over all three panels; back with Esc.
  • Zoomed in, the full resolution is loaded (EXR and 4K too).
  • Space starts and stops playback. It never presses a button, so it never stops the render.

Previous frame · Play/Pause (plays the finished frames in a loop at the script's fps) · next frame · a slider over all frames · frame number · enlarge (preview over three panels, Esc back). Under the bar: the frame's path, size, resolution, channels and check results.

7 The Chunks and Details panels

Chunks

One row per chunk: Chunk (C01…), Frames (range), Count, State, Process (which renders it), Done, Time, s / frame and Note (why a chunk was rendered again and so on).

Right click: Render again (the chunk again), Show process log (the log of the process that rendered it), Delete frames from chunk (only while the render does not run).

Details

Everything about the render in one place: the script and its snapshot, the Writes and output paths, format, fps, range, Nuke version, the Processes × Threads × Cache it runs with, times and the paths to the logs. Handy when you need to know exactly what was rendered.

8 The Workers and Log panels

Workers: a timeline of the processes

One row per Nuke process (W01–W08), time from left to right. grey: Nuke starts and opens the script (also when it is swapped for a fresh Nuke, labelled again: reload). green: finished chunks (with the chunk number). orange: the chunk rendering now. The chunks of other renders are dimmed (Settings › Dim other renders in Workers). You see at once whether a process stands still, starts again or takes long to open the script.

A right click on a process row opens the same menu as in the System panel (chapter 9).

Log

JKrender's messages and the output of every Nuke process, with the time. Filter: All, JKrender only (only JKrender's messages), Errors and warnings. Open log folder opens the folder with this render's logs: the script snapshot, job.json and the worker_NN.log of every process.

Every process reports in the log how long it took to be ready, split into Nuke starting and opening the script. If starting takes 15 s or more, JKrender warns. A slow start is usually the licence or the pipeline's start-up scripts, not the script itself.

11 How to set up a render

The recommended way for a new or heavy script:

A guide (Ryzen 9950X, 32 threads, 94 GB RAM, RTX 3090 24 GB)

Kind of scriptProcesses × ThreadsWhyMeasured
Light comp, keying, grade8 × 4One Nuke does not use all threads, more processes do.a 4K test script: 8 × 4 the fastest
Heavy comp (Defocus, Denoise, many layers)4 × 8 or 2 × 16One process uses more threads. 8 processes run out of RAM and processes close.heavy comp: 4 × 8 with 12 GB cache 17 fr/min, 2 × 16 16 fr/min
A script whose VRAM grows (GPU nodes)1–2 × 32/16VRAM grows with every frame; more processes do not fit on the card.VRAM +1.7 GB per frame → 1 × 32

How to tell the settings are not good

Short of memory

System › RAM is at the limit, State says wait: RAM …, processes close and start again (grey blocks in Workers). Fix: fewer processes with more threads, or a smaller Cache.

A full graphics card

VRAM at 95 %, processes close for VRAM. JKrender itself suggests fewer processes with more threads (it changes nothing by itself). Fix: fewer processes with more threads (Test this script shows how many), or turn Use GPU off.

CPU not used

CPU threads are mostly empty and RAM has room. Fix: add a process (right click › Add process) or raise Threads.

Long script opening

Grey blocks in Workers are long, Script load is high. At start the Nukes compete for licences and start-up scripts. Fix: longer chunks hide it; it usually has nothing to do with the script itself.
The best measure is the Speed tile (frames per minute). Compare it between settings on the same script, or leave it to Test this script.

12 Test this script

A finished test: the green row is the fastest, the orange one second. Winner test shows how much longer the test took with the others, Winner Whole Shot the same for the whole shot.

Buttons at the top

Create tests looks at the computer (the line under the buttons: CPU, cores and threads, on Intel performance and efficiency cores, RAM, graphics) and makes 7 setups from 1 process with all threads to as many processes as the PC takes: each process at least 4 threads and at least 4 GB cache. On 32 threads and 94 GB: 1×32, 2×16, 3×10, 4×8, 5×6, 6×5, 8×4. Past 64 threads a process gets at most 64 (one processor group in Windows). It replaces everything in the table.

Add test adds a setup of your own (Processes, Threads, Cache and Reload Nuke), Remove test removes the selected ones. Right click on a row: Edit test. Your own tests are kept. The Reload Nuke rule of each setup is in the Reload Nuke Rule column right after Processes x threads: never, memory full or every chunk.

The Cache of each setup is all the RAM for Nuke (the RAM limit, less a reserve for Windows) divided by the number of processes, less the 4 GB a process takes outside its cache. What runs at the moment does not matter.

Frames per setup (top right): how many frames each setup renders in Round 2. When the shot has fewer frames, it says so and renders all of them.

How the test runs

Frames are taken from 6 places spread over the whole shot (from the first frame to the last), a few frames in a row at each. All setups of a round render the same frames.

Round 1: every setup briefly, 3 frames per process of the setup with the most processes (on 32 threads 24 frames), at most 3 minutes. Round 2: the two fastest (and any within 5 % of the best) again with exactly Frames per setup frames, but at least 4 per process (6 processes → 24).

Winner test: how much longer the test took than with the fastest (the same frames, Nuke's start included). Winner Whole Shot: an estimate for the whole shot = the test's time + the remaining frames at Frames / min. The start is paid once, the slower rate on every frame, so on a long shot the difference grows (e.g. test +0:10, whole shot +0:43). The cell's tooltip has both times.

Frames / min is counted once the processes are going: Nuke's start and the first frame of each process do not count; in a long render they happen only once. Frames / s is the same per second.

Columns: Reload Nuke Rule, Avg processes (how many processes rendered on average), Round 1, Round 2 (time of the round, frames, start), Frames / min, Frames / s, Frame, CPU / RAM / GPU / VRAM avg, Fell (processes that fell), Reloads (how often Nuke was reloaded), Winner test, Winner Whole Shot, State. A click on a header sorts; columns can be resized and moved.

Use these settings takes the green row into Settings, Reload Nuke too. Frames go to a test folder and are deleted; the Write's render hooks do not run in a test. Tables stay in ~/.nuke/JKrender/settings/test_results.

The Add test window (and the same Edit test from the right click).

Nothing else should render during a test: it would measure two renders fighting over the PC. The test does not start next to a render.

13 Watching RAM and VRAM

JKrender watches the memory, so Windows never starts swapping and the graphics card does not fill up.

For a process to come back, one process of the size the processes of this render had (until known: its Cache + 4 GB) must fit under the limit, with a 2 % margin and what the running processes are still going to take. What it waits for, the State column in System shows, e.g. wait: VRAM 75 → 69 %: the VRAM is at 75 % and must drop under 69 % for one more process to fit. wait: VRAM 75 → 14 % (3 starting): three processes are still starting and JKrender keeps room for them at full size. More states: wait: 25 s (a process just fell), wait: W03 1st frame (it waits for W03's first frame, to see how much a process takes), wait: VRAM ok, checking (there is room; it checks that it stays).
A full card and nothing moves: when the VRAM is over the limit and no process finishes a frame for longer than 4× the usual frame time (at least a minute), Nuke has likely fallen back to the CPU and all processes wait. The process started last then closes at once and its chunk goes back to the queue.

Reload Nuke

While rendering, Nuke keeps memory it no longer needs: a process of a heavy script can grow from 2 to 7 GB of VRAM in its first ~20 frames. A fresh Nuke starts small again, so more processes fit on the card. With the default When memory is full this happens only when the RAM or VRAM has stayed within 5 % of its limit for 30 s without a break (one reading over it is not enough), and one process at a time: the next only once the new Nuke has rendered its first frame and memory is still near the limit. The others go on rendering meanwhile. A process that gets a fresh Nuke shows busy → reload (VRAM 93 %) in State; nothing is swapped for the last chunks.

There is no VRAM cap per process. Cache (-c) limits only Nuke's RAM cache. The graphics card's memory of one process cannot be capped: Windows cannot do it, and Nuke's Blink cache settings have no effect in a render (measured). So JKrender controls VRAM by the number of processes and by fresh Nukes. Cache is a cache limit, not the whole memory of a process; the real number is in System › RAM.

14 Checks, sounds, crashes and data

Checking the output

A render with a cut-off frame (1030) and a black frame (1031), both found by Check frames and Check pixels by hand: a red bar, red frames in the map, the Problems filter shows only them.

CheckWhenWhat it looks for
Check framesWhen the render ends and after Stop (can be turned off), and with the button. Always when a render opens and before Render.Missing, empty, cut-off and unreadable files (EXR, PNG, JPEG, DPX), suspiciously small frames.
Check pixelsWhen the render ends, when it opens (can be turned off) and with the button.EXR, PNG, JPEG, TIFF and DPX: black, empty and one-colour frames, frames the same as another, a different size, channels and bit depth. In EXR also NaN, inf and compression. Other formats: only identical files.
Movie checkFor MOV, MP4 and MXF.Codec, profile, fps, resolution, timecode and frame count against the Write's settings.

Sound after a render

After the render the checks run in the order Check frames → Check pixels; the sound comes once those that are on are through (with both off, right after the render).

A happy sound: everything is fine. An error sound: the render failed, has broken frames or the pixel check found a problem. A render stopped by hand is silent.

When JKrender goes down

The cards come back the next time JKrender opens (for example with the next render sent from Nuke). What is on disk counts and the Nuke processes left over are ended. A render that was going waits for Render and then renders what is missing. When you close the window normally, nothing comes back.

Render data

Every render writes report.json into its log folder: CPU, RAM and graphics card of this PC, settings, speed, memory peaks, closing for limits, Nuke's start, opening the script and the kinds of nodes in the script. It holds no script names, paths or errors; a script is known only by an ID that stays the same across its versions. When you run into a bug, send the render's log folder.

16 When something does not work

ProblemWhat to do
Nuke processes take long to start (30–50 s)Usually Nuke's start (licence, the pipeline's start-up scripts) while the PC renders. The Log splits it: Nuke started in … / script opened in ….
Processes close and start againRAM or VRAM ran out (State in System, Log). Fewer processes with more threads or a smaller Cache; Test this script shows what is fastest.
State says busy → reloadRAM or VRAM has been near the limit for 30 s; after its chunk the process gets a fresh Nuke (Settings › Reload Nuke). If it happens all the time, more processes run than fit.
The whole render is slower than last timeCheck the Cache: too small (e.g. 4 GB for a heavy script) means Nuke throws away and computes again, and frames take several times longer.
The script opens in Nuke with a knob errorE.g. LensDistortion2.serialiseKnob: Failed to load (a node from another version, a missing plug-in). JKrender renders on, as Nuke does in the GUI; the message is in the process's log.
Yellow bar "not checked"The frame check is off (Check frames when a render ends) or did not run. Press Check frames.
Red card or barThe card's tooltip says what went wrong; Output › the Problems filter shows which frames. Right click Render this frame / batch. The bar is worked out again after Check frames and Check pixels by hand too.
No EXR previewnumpy/OpenEXR are missing. Delete lib/DECLINED and restart Nuke, or install them as the README says.
The render did not start at onceState Waiting: other renders already use the PC (Max renders at once), or it waits for memory.
Clearing Nuke's cache does not workAfter updating JKrender, restart Nuke once.
Not sure what was renderedThe Details panel and Log › Open log folder (script snapshot and job.json).
Found a bug? Send the author the render's log folder (Open Renders Folder) and a description of what happened.
